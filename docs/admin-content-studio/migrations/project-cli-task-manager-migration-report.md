# CLI Task Manager Project migration (Phase 10)

Source of truth: `src/projects/catalog/cliTaskManagerProject.js`, a bundled JavaScript content definition with declarative guide, checks and language variants. `node scripts/content/migrate-project.mjs --dry-run` converts and validates without Firebase access. `--seed-emulator` requires a loopback Firestore emulator and `FIREBASE_PROJECT_ID=demo-mitutora`; it saves a draft only, never publishes. A different existing draft requires explicit `--overwrite`. The bundled Project remains available as fallback.

## Source inventory and mapping

The source has ID and slug `cli-task-manager`, title **CLI Task Manager**, Beginner difficulty and a 180-minute estimate. It supports Python, JavaScript, Java and C++. The five checkpoints, in original order, are `setup`, `task-model`, `operations`, `storage` and `integration`. There are no source task objects: the existing Phase 2/7 compatibility adapter derives one task from each checkpoint, with deterministic IDs. This is the only task-boundary transformation; no new curriculum tasks or implementation contracts were invented.

| Item | Source | Canonical draft | Mapping |
| --- | ---: | ---: | --- |
| Languages | 4 | 4 | Same IDs and order |
| Checkpoints | 5 | 5 | Same IDs, order, titles, objectives, requirements and completion messages |
| Explicit tasks | 0 | 5 | One adapter-derived task per checkpoint |
| Guide blocks | 33 | 33 | Two global blocks placed before `setup` guide; 31 checkpoint blocks retain order |
| Starter files | 1 per language | 1 per language | Same runtime-registry starter files and entrypoints |
| Checkpoint checks | 1, 3, 5, 5, 16 | 1, 3, 5, 5, 16 | Declarative trusted descriptors |
| Final checks | 16 | 16 | Declarative trusted descriptors |

The original global guide has a paragraph and runtime command; canonical Project guides are checkpoint-scoped, so these precede the first checkpoint's five blocks. Runtime commands become language-specific `terminal-command` displays. Language-specific hints and snippets remain language-specific guide variants. JavaScript's `index.js` entrypoint/run-command override and all four runtime defaults remain unchanged. The source `languageContent`, `languageOverrides`, artwork, `whatYouWillBuild`, export metadata, original global guide and checkpoint execution modes are retained in migration metadata for published learner adaptation. This provenance is not a separately editable Admin field. Other metadata, learning objectives, prerequisites and skills remain in the canonical envelope/content. No hidden/reference solution was added; mentor context continues to derive from the selected Project/checkpoint content.

Source `source_matches` checks map to trusted `source_pattern` descriptors; `execution` checks map to trusted `runtime_scenario` descriptors. They retain per-language regexes, stdin, required output, visibility, case-insensitive matching, filesystem requirements and expected output-file checks. The persistence second-run scenario carries sandbox files from its preceding scenario. Unsupported Java persistent-file runs remain `not_applicable`, as in the legacy path. The final set retains 16 checks. No executable validator code is imported from content. The migration validates checkpoint/task/check counts, guide counts, starter coverage and the canonical schema, and fails on unknown root/checkpoint/guide/check fields or an unexpected checkpoint/language count instead of silently dropping them.

The only structural differences are the adapter-derived task wrappers and placement of the two global guide blocks under `setup`. The source's per-checkpoint completion messages remain in checkpoint content; the canonical final-completion presentation is generated by the existing adapter. The source's exact final sentence remains in the `integration` checkpoint, but the final presentation sentence is not byte-identical. The original bundled content has not been edited or removed.

## Local acceptance

Project dry-run conversion plus validation took about 65–73 ms. The serialized draft was 47,584 bytes. In the local Firestore emulator, the Project was seeded as one Admin draft alongside the real migrated Python Course and 200 real Python Practice drafts (202 drafts total). No production Firebase was accessed or changed.

Storage layout: the Project draft is one `adminContentDrafts/cli-task-manager` Firestore document. The Course draft has a small root document plus one `courseModules` subdocument; Practice drafts store their bounded serialized document in each root document. Published versions use metadata documents beneath `publishedContent/{id}/versions` and immutable JSON artifacts in the Storage emulator. The Project does not require Course-style draft segmentation at its current size.

Project Studio opened the migrated draft, navigated checkpoints/tasks, edited and saved metadata, a guide paragraph, validator failure message, mentor context and a Python starter file; it reloaded, validated and previewed all four languages. Preview showed selected-language guide/code, starter workspaces, validators and completion content without other-language examples. Browser-observed Admin Project load was about 323–541 ms across local runs. The Project Studio's validator editor supports its existing descriptor fields, but does not yet expose arbitrary descriptor configuration editing; language-variant guide blocks and migration provenance fields are likewise not independently editable. These are Admin authoring limitations, not migration-time content loss.

The local publication test moved real Project, Course and three Practice items through v1 ACTIVE, a metadata-only v2, rollback to v1 and archive. Exact v1/v2 artifacts remained readable after rollback/archive. Project artifacts were 47,668 bytes (v1) and 47,697 bytes (v2); first publication took about 391 ms. Course artifacts were 173,580/173,609 bytes; first publication about 417 ms. Representative Practice artifacts were 1,721/1,750, 3,417/3,446 and 3,071/3,100 bytes; first publications about 153, 131 and 138 ms. These are local observations, not production latency promises.

An authenticated learner-browser smoke used real migrated content with test publication and Firebase Auth/Firestore emulators. The canonical CLI Task Manager appeared once despite the same-ID bundled legacy Project, opened, selected Python, started with content version 1, verified a real task and restored state after reload. The same session discovered the real Python Course, enrolled, ran a Python compiler example, answered a quiz and restored its pinned lesson/version; it also ran an incorrect then correct solution for real migrated Practice, verified the solve and restored it after reload. Course and Practice same-ID canonical precedence was checked. A focused progression test takes the migrated Project through every task, checkpoint and final validation with trusted success evidence; the browser smoke did not manually finish all five real CLI Task Manager checkpoints.

In one local browser run, navigation plus visible-content waits took approximately 2,310 ms for Project open, 1,438 ms for Course overview and 1,191 ms for Practice detail. These include navigation and rendering, not only data fetch time. The local browser suite's emulator helper emitted an exit warning during teardown after the test had passed; no learner assertion failed.

After archive, new discovery hid canonical items while exact pinned Project/Course versions and Practice solve history remained accessible. The local emulator was stopped after testing. No learner production progress was migrated. No production publication, commit or deployment occurred.
